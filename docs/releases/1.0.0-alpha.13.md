# Ontahi 1.0.0-alpha.13 — candidate guide

Status: prepared for the generated release PR; not a publication announcement.

All sixteen packages advance together. The Changesets release workflow owns the exact versions,
package changelogs, immutable artifacts, tag, and publication. This guide describes the accumulated
candidate as one architectural release rather than replaying the order of its implementation PRs.

## Release thesis

Alpha.13 is the release where Ontahí's application model, execution model, and extension boundary
become one coherent system.

Model Support supplied the pressure. A model should not receive a parallel collection of ad hoc
tools; it should propose the same parameterized Graph Reads, Graph Commands, and Operations that
the rest of the application already understands. Those canonical applications may contain typed
holes, be completed through an Interaction, be revalidated under current authority, and only then
execute.

That requirement forced the runtime boundary to become explicit. Runtime Protocol now carries the
same application requests and observations across local execution, Fetch, WebSocket, Express,
Next.js, Devtools, and durable executors. The emerging Semantic Program Kernel is therefore not a
new agent API. It is the shared language formed by Reads, Commands, Operations, Interactions,
Events, and resumable continuations.

Events complete the other direction of the model. Operations express an intention to change the
application; Events express accepted facts. Typed declarations, post-commit occurrences, fan-out,
external ingress, durable delivery, Task waits, browser observation, and Devtools inspection now
share that distinction without exposing a broker or HTTP framework as the domain API.

## The extension model

Provider packages are collections of independently selectable Ontahí capabilities, not generic
technology clients. `@ontahi/postgres`, for example, can provide Data Graph storage, Task Storage,
an Event Runtime, or any combination. `@ontahi/runtime-vercel-workflows` and
`@ontahi/runtime-langgraph` implement the Task execution boundary while Core continues to own the
public Task and Interaction contract. Express and Next.js project the same receiver and Event
ingress contract into different host frameworks.

This is the intended community boundary: implement one concern faithfully, advertise only the
guarantees the provider can preserve, and prove it with the shared conformance suite. See the
[adapter capability matrix](../developers/03-runtimes/05-adapter-capability-matrix.md) for the exact
current combinations and limitations.

## Upgrading a host

Pin every direct `@ontahi/*` dependency to exactly `1.0.0-alpha.13` and commit manifests and lockfile
together. Regenerate browser clients and durable Task artifacts, check generated drift, then run
host typechecks, authorization-sensitive integration tests, and a production build. Do not mix
alpha.12 and alpha.13 packages or commit a floating `alpha`/`latest` range.

Review these integration points explicitly:

1. Compose one application Runtime Protocol receiver and project it through the chosen host rather
   than maintaining family-specific endpoints.
2. Configure persistent `TaskStorage` when explicit durable executions must survive restart.
   Function-style continuations still require the originating process.
3. Treat model-produced applications as untrusted proposals and preserve revalidation at execution.
4. Select Event Runtime guarantees intentionally. The default is ephemeral; durable waits require a
   runtime with retained delivery and atomic claim support.
5. Keep Event ingress default-deny and authenticate the provider's original request before
   normalization. Provider delivery identity is provenance, not automatic deduplication.
6. Regenerate any reflection/codegen consumer after adding Events, parameterized applications, or
   changed Operation input semantics.
7. If adopting PostgreSQL, MySQL, or Supabase Task Storage, install and grant the provider-owned
   schema/RPC surface documented by that adapter. Package installation never migrates production
   storage automatically.

## Known limits and the next release line

- Durable idempotency policies are reflected but not yet enforced. Repeated ingress can start a new
  run depending on the application path. Plan 132 owns durable invocation identity, retry, and
  deduplication semantics and is the natural opening focus for alpha.14.
- Task snapshots can represent `cancelled`, but there is no general durable cancellation request or
  shared cancellation capability across executors.
- Event observation is live-only. There is no general Event history, cursor replay, automatic
  resubscription, broker adapter, or generalized durable Event processor.
- Event declaration versions match exactly. Cross-version migration and delivery are not inferred.
- LangGraph rejects Event waits because its adapter cannot yet prove the durable delivery and atomic
  Task-claim contract. Vercel Workflow and the native explicit executor support them.
- Supabase supplies durable Task Storage but no Event Runtime.
- Data Graph commits, Task writes, and Event acceptance are separate concerns. Reusing one provider
  or connection pool does not make them atomic.

These are release boundaries, not hidden guarantees. None should be papered over by a host-specific
retry loop or by interpreting provider behavior as an Ontahí contract.

## Candidate evidence and publication gate

The release-readiness branch is based on `99b752f0`, the main commit that closed the first-class
Events architecture and adapter capability inventory. Its local rehearsal passed:

- build and typecheck for all sixteen packages plus Todo and Classroom;
- repository and workspace lint, formatting, and generated-code drift checks;
- 3,341 package tests across all sixteen packages, including real PostgreSQL, MySQL, and Supabase
  provider suites;
- Todo's 175 tests and Classroom's 8 default tests; Classroom's 5 opt-in PostgreSQL tests remained
  skipped by the standard example command;
- deterministic double-pack verification plus clean-consumer install, public-entrypoint typecheck,
  and runtime smokes for all sixteen packages;
- preparation of `.artifacts/npm/candidate/release-manifest.json` and offline npm dry-run for all
  sixteen tarballs.

Because versions are bot-owned, the main-branch rehearsal tarballs still carry the current
`1.0.0-alpha.12` manifests. They validate the post-alpha.12 source payload and release machinery;
they are not the publishable alpha.13 candidate. `changeset status` confirms that all sixteen
packages, including the new `@ontahi/runtime-langgraph`, participate in the alpha.13 bump. The
generated release PR must repeat artifact preparation after applying its alpha.13 versions.

The generated `Release Ontahi 1.0.0-alpha.13` pull request remains the only owner of versions,
changelogs, tags, and publication. It must be refreshed from main and pass its GitHub, security, and
quality gates after this documentation PR merges. Local rehearsal success is evidence, not
permission to bypass a failing release workflow.
